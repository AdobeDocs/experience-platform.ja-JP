# 計算属性の概要

マーケターがパーソナライゼーションの効果を最大化するには、顧客の行動にもとづくPersonalizationが不可欠です。 例えば、最近閲覧した商品を使ってマーケティングメールをパーソナライズし、コンバージョンを促進したり、利用者の購入総数にもとづいてweb ページをパーソナライズしてリテンションを促進したりすることができます。

計算属性は、次のようなエンジニアリングリソースに依存することなく、プロファイル行動データをプロファイルレベルで集計値にすばやく変換するのに役立ちます。

- Real-Time Customer Data Platformの宛先に対する行動集計のアクティベーションと、Adobe Journey Optimizerでの使用により、ターゲットを絞った一対一のパーソナライゼーションやバッチパーソナライズが可能になります
- 行動集計をプロファイル属性として保存し、オーディエンスのセグメンテーションを簡素化
- プラットフォームやアプリをまたいで利用するための、集約されたプロファイル行動データの標準化
- 古いプロファイルイベントデータを統合して、より優れたデータ管理を実現

これらの集計は、Adobe Experience Platformに取り込まれた、ユーザーが作成したプロファイル対応のExperience Event データセットに基づいて計算されます。 つまり、Adobe Journey Optimizer システムデータセット **など、SDKを介してサービストークンを介して作成されたシステム生成データセットは使用できません**。

各計算属性は、プロファイル結合スキーマで作成されたプロファイル属性で、結合スキーマの「SystemComputedAttribute」フィールドグループにグループ化されます。

ユースケースの例には、次のようなものがあります。

- 合計リワードポイントを含むマーケティングメールをパーソナライズして、ユーザーがプレミアム階層に昇格したことを祝福します
- 購入回数や頻度にもとづいて、利用者へのコミュニケーションをパーソナライズ
- サブスクリプションの有効期限に基づくリテンションメールのパーソナライズ
- 最後に閲覧した商品の商品を閲覧したが購入しなかった利用者をリターゲティングする
- Real-Time CDP Destinationsを使用して、計算属性を使用してイベント集計をダウンストリームシステムにアクティベートする
- 複数のイベントベースのオーディエンスを、より凝縮された計算属性のグループに集約する
- イベントからの最近のパートナーIDを使用して、オフサイトの未認証のユーザーをリターゲティングする

このガイドでは、計算属性の基本的な説明に加えて、Experience Platform内の計算属性の役割をより深く理解するのに役立ちます。

## 計算済み属性について

Adobe Experience Platformを使用すると、複数のソースからデータを簡単に読み込んで結合し、[!DNL Real-Time Customer Profiles]を生成できます。 各プロファイルには、顧客の連絡先情報、好み、購入履歴など、顧客に関する重要な情報が含まれ、顧客の全体像を把握することができます。

プロファイルで収集された情報には、データフィールドを直接読み取る場合にわかりやすい（「名」など）ものや、情報を生成するために複数の計算を実施するもの、他のフィールドの値に依存するもの（「ライフタイム購入合計」など）があります。このデータを一目で理解しやすくするために、[!DNL Experience Platform]では、これらの参照と計算を自動的に実行する計算属性を作成し、適切なフィールドに値を返すことができます。

計算属性には、入力データに対して操作し、結果の値をプロファイル属性に格納する式（ルール）の作成が含まれます。 式は複数の異なる方法で定義でき、集計するイベント、集計関数、ルックバック期間を指定できます。

### 関数

計算属性を使用すると、定義済みの関数を活用してセルフサービス方式でイベント集計を定義できます。 これらの関数の詳細は次のとおりです。

| 関数 | 説明 | サポートされているデータタイプ | 使用例 |
| -------- | ----------- | -------------------- | ------------- |
| SUM | **合計**&#x200B;個の関数が、修飾されたイベントに対して指定された値を増やします。 | 整数、数値、ロング | 過去7日間のすべての購入合計 |
| カウント | 指定されたルールに対して発生したイベントの数を&#x200B;**カウント**&#x200B;する関数。 | なし | 過去3か月間の購入回数 |
| 最小 | 適格なイベントの&#x200B;**minimum**&#x200B;値を見つける関数。 | 整数、数値、ロング、タイムスタンプ | 過去7日間の最初の購入データ <br/>過去4週間の最低注文金額 |
| 最大 | 選定されたイベントの&#x200B;**最大**&#x200B;値を見つける関数。 | 整数、数値、ロング、タイムスタンプ | 過去7日間の最終購入データ <br/>過去4週間の最大注文金額 |
| MOST_RECENT | 最新の修飾イベントから指定された属性値を検索する関数。 この関数は、**both**&#x200B;に属性の値とタイムスタンプを与えます。 | すべてのプリミティブ値、プリミティブ値の配列 | 過去7日間に表示された最新製品 |

### ルックバック期間

計算属性は一括計算されるため、集計を最新の状態に保ち、最新のイベントを使用できます。 これらのシナリオを最小限の遅延でサポートするために、更新頻度はイベントのルックバック期間によって異なります。

ルックバック期間とは、計算属性のエクスペリエンスイベントを集計する際に確認される時間を指します。 この期間は、時間、日、週、または月で定義できます。

更新頻度とは、計算属性が更新される頻度を指します。 この値はルックバック期間に依存し、自動的に設定されます。

| ルックバック期間 | 更新頻度 |
| --------------- | ----------------- |
| 最大24時間 | 1 時間ごと |
| 最大7日間 | 毎日 |
| 最大4週間 | 毎週 |
| 最大6か月 | 毎月 |

例えば、計算属性に過去7日間のルックバック期間がある場合、この値は過去7日間の値に基づいて計算され、その後、日次で更新されます。

>[!NOTE]
>
>イベントのルックバックで使用される場合、週と月の両方が&#x200B;**カレンダー週**&#x200B;と&#x200B;**カレンダー月**&#x200B;と見なされます。 カレンダー週は&#x200B;**日曜日**&#x200B;に始まり、週の&#x200B;**土曜日**&#x200B;に終了します。 カレンダーの月は、月の&#x200B;**最初**&#x200B;に始まり、月の&#x200B;**最後の日**&#x200B;に終了します。

計算属性のルックバック期間は、**ローリング**&#x200B;のルックバック期間です。 例えば、10月15日にUTCの午前12時に初回評価が発生した場合、2週間のルックバック期間は、10月1日から10月15日までのすべてのイベントを取得し、10月22日の1週間の時間で更新し、10月8日から10月22日までのすべてのイベントを取得します。

**高速更新** {#fast-refresh}

高速更新を使用すると、属性を最新の状態に保つことができます。このオプションを有効にすると、長いルックバック期間であっても、計算属性を毎日更新できるので、ユーザーのアクティビティに迅速に対応できます。

>[!NOTE]
>
>高速リフレッシュを有効にすると、ルックバック期間がそれぞれ週単位または月単位で繰り返されるため、イベントのルックバック期間は異なります。
>
>高速更新が有効になっている2週間のルックバック期間を持つ計算属性を作成する場合、これは最初のルックバック期間が2週間であることを意味します。 ただし、毎日の更新では、ルックバック期間には追加日のイベントが含まれます。 この日数の追加は、次のカレンダー週が始まるまで続き、ルックバックウィンドウがロールオーバーされ、2週間に戻ります。
>
>例えば、3月15日（日曜日）から2週間のルックバック期間が開始され、毎日の更新が有効になっている場合、ルックバック期間は3月22日までさらに拡大し、2週間にリセットされます。 つまり、計算属性は毎日&#x200B;**更新**&#x200B;され、ルックバック期間は&#x200B;**2**&#x200B;週間から&#x200B;**3**&#x200B;週間に増加し、その後&#x200B;**2**&#x200B;週間に戻ります。
